# 工程流程细则

[Skill 入口](../SKILL.md)

为项目建立或调整开发规则时使用；普通文档更新无需重复加载。规则应适合项目规模，不绑定来源项目或特定技术栈。

## 设计到实现

1. 调查项目规范、文档索引、实际代码与依赖版本，区分现状、目标和已验证事实。
2. 保护已有修改。有 Git 时按项目约定使用任务分支；没有 Git、远端或构建入口时如实注明，不因文档初始化自动建立发布流程。
3. 先区分整体交付计划和特性设计：MVP 交付组织在 plan，从需求提炼稳定能力为 feature，不按模块或步骤机械拆分。定位已有 feature，以一句话需求、目标与非目标界定本次增量；引用架构约束，在所属独立里程碑中更新 feature 范围。小任务原地记录，需要单独跟踪才建 plan。
4. 明确最小公开面、执行与失败边界、harness 和可观察退出条件。先完成具体可评审设计，再进行需要的评审。
5. 项目采用人工设计评审时，新特性、架构或公开契约变化在实现前等待明确同意。bugfix 在已有契约内修复可采用免审流程，不能把功能扩大包装成修复。用户已有授权不重复询问。仅整理用户已指定的文档规则不因本 skill 新增审批。
6. 若项目要求编辑器评审，使用 `$EDITOR` 打开实际文件，命令参数安全拆分，不用 `eval`；不可用时说明并提供链接。编辑器退出不是批准。
7. 建立最小纵向 harness，按计划实现并循环验证。核心契约和范围变化时先更新原 feature，按现有审批边界重新评审；不为日常实现选择反复建文档。
8. 记录实际命令、版本或提交、输入、断言、故障、退出结果和证据。同步 feature 当前设计、里程碑阶段范围和任务状态。产品行为变化更新适用产品文档与变更说明，工程文档变化不编造产品发布记录。
9. 依授权交付，提交或 PR 引用 feature、独立任务和实际验证，不宣称未执行检查通过。没有 Git/远端时也可以完成本地文档任务，不自动初始化或发布。

## 可重复验证

验证入口应调用生产边界，不复制业务算法。用确定性替身隔离模型、时间或网络时说明替代范围，保留真实受测路径。对相关并发、失败、取消和资源释放提供观察结果；与任务无关的场景不机械添加。

一个 loop 的记录可以很短：场景、命令、预期与实际差异、修正、重跑结论。已有 bug 应先证明复现，修复后使用相同输入验证。无法自动化的步骤写人工操作与判据，不能把“看起来正常”当作结论。

UI 相关任务直接链接 UI 指导并验证真实操作；仅调用后端不能替代交互验证，界面空闲或停止输出不能证明任务成功。未验证平台单独标明。

证据可直接写入 feature 或 plan；确需附件再设置证据目录，避免为小任务新增报告、截图索引和重复总结。保留必要失败证据，先脱敏，不提交临时产物或凭据。

## 收敛、归档与迁移

架构、阶段总览、独立里程碑、UI 指导、harness、feature、plan、refctory、bugfix 和独立 research 均以首次创建日期结尾；AGENTS.md、README.md 与模板入口不加日期。迁移时依据文档记录或 Git 历史确认创建日期；无法确认时明确记录采用的日期依据，不伪造原始日期。更新正文不改变文件名日期。

完成任务后把最终职责、接口、限制和验证入口收敛回同一 feature，保留首次创建日期；旧决策必要时简记原因与替代。不要让 feature 变成无限追加的任务日志。

plan、独立 refctory、bugfix 完成且证据齐全后可归档；feature 只有在整个特性退役或被替代时归档。采用 `archive/YYYY-MM/<原文件名>` 或兼容项目已有规则，记录状态、日期、原因和替代链接，移动后修复入站与出站引用。

整理已有文档先列出到 canonical feature 的映射，保留唯一当前契约；不要未经确认删除含独有决策或证据的旧稿。结构调整不应改写历史验收事实。每阶段里程碑保留自身范围与证据，总览只链接各阶段。
