# Skill 编写规范

## 目标

Skill 应补充模型不知道的团队上下文、确定性流程或风险约束，而不是复述通用常识。一个 Skill 要有清晰触发场景，也要说明容易误触发的边界。

## 最小结构

```text
my-skill/
├── SKILL.md
├── scripts/       # 只有重复且需确定执行的逻辑才放这里
├── references/    # 只在特定场景加载的详细资料
└── assets/        # 输出时会复制或改造的模板、图片等
```

`SKILL.md` 必须以 YAML frontmatter 开始：

```yaml
---
name: my-skill
description: 做什么、什么时候使用，以及必要的排除边界。
---
```

## 编写原则

- 让 `description` 足够准确，使客户端只在相关请求中加载它。
- 主文件只保留共同流程和关键约束；条件性细节放入 `references/`，并明确何时读取。
- 重复执行、容易手误或必须得到稳定结果的操作写成 `scripts/`，脚本需有测试。
- 示例全部使用虚构数据，不含凭据、客户信息、手机号或本机绝对路径。
- 外部写入、删除、发布、付款等动作必须保留用户授权边界和停止条件。
- 不绑定某一模型的思维方式；描述可观察结果、工件和验收标准。
- 修改已有 Skill 时保持兼容，破坏性变更在 PR 中明确迁移方式。

## 多平台要求

- 安装、更新、卸载和 Agent 路径适配统一交给 `npx skills`；仓库脚本不要另建一套包管理状态。
- Session Hook 等团队特有自动化优先使用 Python 3.9+ 标准库；不要把 Bash 当作所有成员都具备的运行时。
- 路径使用相对路径或运行时解析，不能提交某位成员的 home 目录。
- 必须区分 shell 命令与 Skill 本身的能力：平台专属命令需同时给出 Windows 和 Unix 方案，或明确降级路径。
- 链接与 copy 的平台差异由 `npx skills` 处理；团队文档只暴露它的标准参数。
- 新增成员端工具时，至少在 Linux、macOS、Windows CI 上验证入口、路径和失败退出状态。

## 外部 Skill

- 不直接复制第三方 Skill；在 `catalog.json` 记录官方 Git URL、不可漂移的 tag 或 commit、Skill 子目录和许可证。
- 禁止把外部来源锁定到可变的 `main`、`latest` 或未固定分支。
- 升级前复核上游 diff、许可证、安装脚本和新增依赖，再由中央清单统一提升 `ref`。
- 外部 checkout 是只读分发源；检测到本地修改时，`sync` 必须停止而不是覆盖。

## 版本与稳定性

- `experimental`：正在验证，默认不安装。
- `beta`：接口基本稳定，仍需收集反馈。
- `stable`：团队推荐使用，变更需兼容性复核。
- `deprecated`：停止新采用，说明替代方案后再移除。

稳定性登记在根目录 `catalog.json`。默认安装应只面向足够通用、维护责任明确的 Skill。

团队采用策略与稳定性是两个维度：`required` 表示组织强制，`recommended` 表示建议采用，`deprecated` 表示成员应迁出。把 Skill 调整为必装或废弃属于团队策略变更，PR 中必须说明影响和迁移方式。
